# 小组件模块通用设计

> 本文描述灵月桌面小组件系统的通用架构、当前能力和后续 Agent 控制设计。具体组件能力见同目录下各组件文档。

## 1. 模块定位

小组件是显示在桌面透明画布窗口上的可交互信息层。它们不是纯静态装饰，而是可以被主界面、画布交互和未来 AI Agent 共同管理的桌面对象。

AI 对整套桌面进行场景化布置时，应以 `AI桌面编排系统设计.md` 为主文档；本文只描述单个组件系统的通用能力和控制接口。

当前小组件承担三类功能：

| 类型 | 说明 | 例子 |
| --- | --- | --- |
| 悬浮挂件 | 无固定卡片背景，以内容本身为主体，可通过浮动工具栏改样式 | 时钟、天气、音频可视化、白噪音、桌面文字 |
| 卡片组件 | 有固定尺寸和毛玻璃背景，用于承载信息面板 | 日历、新闻、自选股、快捷工具、系统监控 |
| 图标收纳 | 桌面快捷方式托管层，跨壁纸全局保存 | 纵向收纳、横向收纳、自适应收纳、桌面 Dock |

## 2. 当前通用实现

### 2.1 数据模型

小组件统一使用 `WidgetInstance`：

| 字段 | 作用 |
| --- | --- |
| `id` | 单个组件实例 ID |
| `type` | 组件类型，例如 `clock`、`weather`、`desktop-icons-dock` |
| `x / y` | 桌面画布坐标 |
| `width / height` | 组件尺寸 |
| `enabled` | 是否启用 |
| `config` | 组件私有配置，按组件类型解释 |

当前定义位置：`src/shared/types.ts`。

### 2.2 运行链路

1. 主界面 `WidgetsPage` 提供组件目录、预览、添加和部分设置入口。
2. `window.lingyue.widget.add/update/remove/updateConfig` 通过 IPC 进入主进程。
3. `widgetIpc` 负责组件放置、网格吸附、边界约束、重叠避让、自动保存和同步。
4. 组件画布窗口通过 `WIDGET_SYNC` 接收列表，并由 `src/renderer/widgets/index.tsx` 根据 `type` 渲染具体组件。
5. 壁纸切换时，普通组件读取对应壁纸目录下的 `widget-config.json`；图标收纳类组件作为全局组件保存。

### 2.3 布局与保存

当前已实现：

- 添加组件时自动寻找不重叠位置。
- 移动组件时进行网格吸附、边界约束和重叠避让。
- 普通组件配置随壁纸保存到 `assets/wallpaper/<id>/widget-config.json`。
- 图标收纳/Dock 组件跨壁纸全局保存。
- 自动保存使用 500ms 防抖，切壁纸前会取消旧保存任务。
- 编辑模式统一控制 z-order、鼠标穿透和焦点。

### 2.4 视觉与配置共性

当前通用能力：

- `FrostedGlassBackground` 用壁纸抽帧实现毛玻璃背景。
- `COLOR_THEMES` 提供统一颜色主题。
- `FloatingToolbar` 支持悬浮挂件样式、主题、明暗、透明度、图标收纳外观、Dock 外观等设置。
- 部分组件支持 `style`、`themeId`、`darkMode`、`opacity` 等通用配置。

需要继续统一：

- 所有组件的配置 schema 还没有集中登记。
- 哪些配置可由 UI 修改、哪些可由 Agent 修改，目前靠组件代码约定。
- 数据型组件的数据源、缓存、错误兜底没有完全统一。

## 3. 当前边界

当前小组件系统已经具备运行能力，但还缺少“可被 Agent 稳定控制”的结构化层：

| 问题 | 当前状态 |
| --- | --- |
| 组件 schema | 分散在组件代码和设置页里 |
| 组件动作 | 没有统一 action 定义，例如播放白噪音、刷新新闻、添加股票 |
| 组件状态 | 缺少统一的状态读取接口 |
| Agent 审计 | Agent 修改组件时还没有专门的操作记录 |
| 回滚 | 依赖组件配置文件或 store，没有组件级 diff/rollback UI |
| 权限 | 还没有区分只读查看、布局修改、数据修改、外部动作 |

## 4. 未来 Agent 控制设计

未来目标是让用户可以在 AI 对话里直接说：

- “把天气放到右上角，换成霓虹样式。”
- “给自选股加上比亚迪和招商银行。”
- “把桌面 Dock 调透明一点，图标放大一些。”
- “创建一个工作模式布局，把新闻和股票放到左侧。”
- “把白噪音切到雨声，音量调低。”

这需要在现有 IPC 外面增加一层类似 MCP 的本地组件控制协议，可称为 Widget Control Protocol。它不必真的依赖外部 MCP 服务，但设计上应像工具协议一样结构化、可审计、可回滚。

### 4.1 组件注册表

新增统一注册表，记录每种组件的元数据：

| 字段 | 说明 |
| --- | --- |
| `type` | 组件类型 ID |
| `displayName` | 用户可读名称 |
| `category` | floating / card / icon-storage |
| `defaultSize` | 默认尺寸 |
| `allowMultiple` | 是否允许多实例 |
| `configSchema` | 可配置字段、类型、默认值、取值范围 |
| `actions` | 可执行动作，例如 refresh、play、pause、addSymbol |
| `stateSchema` | 可读取状态，例如当前播放声音、股票列表、天气城市 |
| `agentHints` | Agent 用自然语言理解组件用途的说明 |

### 4.2 Agent 工具建议

建议暴露给 AI Chat / Agent 的工具层：

| 工具 | 作用 | 风险 |
| --- | --- | --- |
| `widget_list` | 列出当前桌面组件和布局 | 低 |
| `widget_get` | 查看单个组件配置、状态和可用动作 | 低 |
| `widget_create` | 添加组件实例 | 中 |
| `widget_update_layout` | 移动、缩放、启用、禁用组件 | 中 |
| `widget_update_config` | 修改组件配置 | 中 |
| `widget_invoke_action` | 执行组件动作，例如刷新、播放、暂停 | 中 |
| `widget_remove` | 删除组件实例 | 高 |
| `widget_snapshot` | 创建布局快照 | 低 |
| `widget_restore_snapshot` | 恢复布局快照 | 高 |

### 4.3 正式组件接口索引

Agent 不应只根据组件文件名猜字段。正式组件需要在文档中明确“可读状态、可改配置、可执行动作”，并由组件注册表把这些能力暴露出来。

| 能力模块 | 类型 ID | 文档 | 主要 Agent 动作 |
| --- | --- | --- | --- |
| 时钟组件 | `clock` / `elegantclock` / `pixelclock` / `graphicdatetime` | `doc/小组件/时钟组件设计.md` | `time.create`、`time.switch_variant`、`time.apply_style`、`time.generate_style_from_wallpaper` |
| 音频可视化 | `audio` | `doc/小组件/音频可视化组件设计.md` | `audio.set_style`、`audio.set_source`、`audio.set_reactivity`、`audio.generate_style_from_wallpaper` |
| 图标收纳 | `desktop-icons-box` / `desktop-icons-horizontal` / `desktop-icons-adaptive` / `desktop-icons-dock` | `doc/小组件/图标收纳组件设计.md` | `icons.import_items`、`icons.restore_item`、`icons.reorder_items`、`icons.organize_by_rule` |
| 天气 | `weather` | `doc/小组件/Weather 天气.md` | `weather.set_city`、`weather.set_style`、`weather.refresh`、`weather.use_location` |
| 白噪音 | `whitenoise` | `doc/小组件/WhiteNoise 白噪音.md` | `noise.play`、`noise.pause`、`noise.set_sound`、`noise.set_volume`、`noise.set_timer` |

### 4.4 权限与审计

Agent 控制组件时应遵守四级权限：

| 权限 | 允许行为 |
| --- | --- |
| read-only | 只能查看组件和布局 |
| ask-before-layout | 移动、缩放、添加前需要确认 |
| ask-before-action | 播放声音、打开程序、修改股票列表等动作前需要确认 |
| workspace-write 等价授权 | 在用户明确授权后可批量调整布局和配置 |

每次 Agent 修改组件都应记录：

- 操作前配置。
- 操作后配置。
- 影响组件 ID。
- 用户请求原文。
- 是否经过确认。
- 是否可回滚。

### 4.5 配置变更流程

推荐流程：

1. Agent 读取当前组件列表。
2. Agent 根据组件 schema 生成计划。
3. 对布局、删除、外部动作等风险操作请求用户确认。
4. 创建组件布局快照。
5. 调用结构化工具修改布局或配置。
6. 同步到画布并保存到当前壁纸配置。
7. 返回变更摘要和可回滚入口。

### 4.6 组件动作与状态

每个组件后续都应补齐三种能力：

| 能力 | 说明 |
| --- | --- |
| Read State | 让 Agent 知道组件当前显示什么、播放什么、配置是什么 |
| Update Config | 让 Agent 能稳定修改配置而不是猜字段 |
| Invoke Action | 让 Agent 能执行组件动作，例如刷新新闻、切换白噪音、添加自选股 |

### 4.7 和现有 IPC 的关系

Widget Control Protocol 不替代现有 IPC，而是包装现有 IPC：

- 底层继续使用 `WIDGET_LIST`、`WIDGET_ADD`、`WIDGET_UPDATE`、`WIDGET_UPDATE_CONFIG`、`WIDGET_REMOVE`。
- 图标收纳继续使用 `DESKTOP_ICON_IMPORT`、`DESKTOP_ICON_LAUNCH`、`DESKTOP_ICON_CONTEXT_MENU`。
- 数据型组件继续通过主进程服务拿数据。
- Agent 工具层负责 schema 校验、权限确认、审计和可回滚记录。

## 5. 后续优先级

| 优先级 | 任务 |
| --- | --- |
| P0 | 建立组件注册表和统一 config schema |
| P0 | 统一天气、系统信息、新闻、股票等数据服务入口 |
| P1 | 增加组件布局快照和恢复 |
| P1 | 接入 Agent 工具：list/get/update_config/update_layout |
| P1 | 给数据型组件增加统一 refresh action |
| P2 | 增加组件事件流，让 Agent 能理解组件近期状态变化 |
| P2 | 做多布局方案，例如工作、休息、专注模式 |
