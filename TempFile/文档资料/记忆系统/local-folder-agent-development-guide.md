# 灵月轻量桌面助手与组件操作设计规格

> 资料角色（2026-09-05 核对）：本文件是轻量助手的产品规格，含待实现目标；当前状态见 [项目状态](../project-status.md)。它不替代根目录开发规则，也不取消现有高风险工具的权限校验。

整理日期：2026-05-25

> 方向修正：本文替代旧版“本地文件夹 Agent 软件完整设计规格”。灵月不是 Codex 式编程 Agent，电脑操作只是 AI 伴侣的辅助能力。后续设计以“有形象、有温度、会陪伴、能顺手帮忙”为核心，避免把产品体验拉向严肃的文件审查、回滚、审批和复杂任务面板。

## 1. 产品定位

灵月的 AI 模块首先是桌面 AI 伴侣，其次才是轻量桌面助手。

用户打开聊天时，应该感觉自己在和一个熟悉的角色说话：她有语气、有表情、有等待动作，会记得用户偏好，也能在需要时顺手查天气、生成便签、调整桌面组件、打开网页或整理一点简单信息。

不追求第一版完成复杂能力：

- 不以编程、批量文件修改、命令执行为核心。
- 不默认展示复杂 AgentRun、checkpoint、diff、审批历史。
- 不把工具日志当成主体验。
- 不鼓励模型把简单对话变成任务流。

核心体验目标：

- 对话像人，反馈自然，有角色连续性。
- 桌宠形象、状态、说话内容和 UI 反馈一致。
- 用户可以用自然语言生成或调整桌面组件。
- 用户可以让灵月做轻量电脑操作，但过程不打扰。
- 有风险的动作简单确认，低风险动作直接完成并给温柔反馈。

## 2. 能力分层

### A. 伴侣对话层

这是第一优先级。

能力包括：

- 流式聊天。
- 人设与称呼。
- 情绪识别和安慰。
- 轻松闲聊、吐槽、陪伴、鼓励。
- 根据上下文自然提起少量记忆。
- 通过桌宠动作表现正在思考、开心、认真、担心、搜索中等状态。

完成质量看这些指标：

- 回复是否像同一个角色。
- 是否能识别用户情绪，不机械套模板。
- 是否能自然收束，而不是长篇工具报告。
- 等待和工具过程是否像角色行为，而不是系统日志。

### B. 记忆与关系层

记忆服务伴侣感，不服务知识库堆叠。

优先记住：

- 用户喜欢的称呼、语气和互动边界。
- 稳定偏好，例如颜色、组件风格、工作习惯。
- 情绪强度较高的事件。
- 长期目标、近期计划和反复提到的问题。
- 对桌面组件和桌宠行为的偏好。

不应默认记住：

- 普通闲聊。
- 临时搜索结果。
- 一次性的文件路径。
- 工具中间日志。
- 大量编程细节和命令输出。

私密记忆必须单独处理，不进入普通陪伴、桌面助手和轻工作场景。

### C. 桌面组件层

这是未来主线之一。

用户可以说：

- “给我放一个今晚 8 点提醒的便签。”
- “把天气卡片换成更可爱的样子。”
- “生成一个今天待办的小组件。”
- “这个股票卡片太占地方，帮我缩小一点。”
- “把白噪音组件调成雨声，小声一点。”

组件能力优先级：

1. 读取当前组件列表和状态。
2. 根据对话生成组件草案。
3. 让用户轻确认后添加到桌面。
4. 修改组件内容、样式、位置、尺寸。
5. 记录“这个组件来自哪次对话”和“最后由 AI 修改了什么”。

组件操作反馈应像对话：

```text
好，我给你放一张小小的待办卡。先用清爽一点的样式，别太抢桌面。
```

而不是：

```text
create_widget completed. config saved.
```

### D. 轻量电脑操作层

电脑操作是辅助，不是主舞台。

第一版建议覆盖：

- 获取时间、天气、新闻、搜索结果。
- 打开 URL、文件夹或常用应用。
- 读取/写入剪贴板。
- 创建简单文本、Markdown、CSV、便签内容。
- 小范围读取用户选择的文件。
- 简单整理用户明确选择的一小组文件。
- 截图、记录灵感、生成清单。

暂缓或隐藏为高级能力：

- 批量重命名。
- 大范围移动/删除文件。
- 命令执行。
- 编程项目修改。
- 复杂 checkpoint/rollback。
- 长任务自动化。

这些高级能力可以保留代码骨架，但不应成为默认 UI 和文档主线。

### E. 打包后的自修复与运行时可变层

灵月后续可以具备“检查并修好自己一部分问题”的能力，但必须先区分可变层和不可变层。打包后的应用本体、内置资源和主进程能力不应被 AI 直接修改；AI 能安全处理的是运行时数据、用户生成内容和受控扩展包。

不可直接自修复的部分：

- `main/preload/renderer` 核心代码、IPC 桥、工具注册表、模型调用适配层。
- 安装包内的 `resources/assets`、asar 内容、构建配置和原生依赖。
- 系统权限、Windows 安装目录、签名、自动更新机制。
- 会影响所有用户的默认内置壁纸和默认组件配置。

可以由 AI 检查、提示或修复的部分：

- `electron-store` 中的模型、人设、壁纸状态、组件状态。
- SQLite 对话、记忆、工具事件和轻量动作记录。
- `userData/wallpapers/<id>/` 用户导入壁纸。
- `userData/wallpaper-overrides/<wallpaperId>/settings.json` 壁纸设置覆盖。
- `userData/wallpaper-overrides/<wallpaperId>/widget-config.json` 组件覆盖配置。
- `userData/desktop-icons/<widgetId>/` 图标托管数据。
- 未来的 `userData/components/` 或类似目录中的对话生成组件包。

对用户的表达方式也要分层：

```text
我看到了，是这个组件自己的配置乱了。我可以帮你整理一下。
```

```text
这个像是应用本体里的问题，我现在不能在这里直接改核心程序，需要通过下一次应用更新修。
```

未来“组件自生成/自修复”应只发生在受控扩展层：每个组件包有 manifest、schema、权限声明和版本号；运行前先校验，修复时只替换该组件包或它的配置，不触碰主程序。

## 3. 核心对象

### CompanionSession

一次用户和灵月的持续对话。

字段：

- `id`
- `mode`: `daily` / `emotion` / `desktop` / `light-work` / `private`
- `title`
- `personaId`
- `currentMood`
- `currentTopic`
- `createdAt`
- `updatedAt`

### CompanionState

当前角色状态，影响回复、桌宠动作和 UI。

字段：

- `personaName`
- `relationshipTone`
- `petState`
- `emotionHint`
- `isThinking`
- `currentActionSummary`
- `lastUserMood`
- `lastCompanionGesture`

### CompanionAction

一次轻量动作。

字段：

- `id`
- `sessionId`
- `type`: `search` / `weather` / `open` / `clipboard` / `component` / `note` / `file-light`
- `status`: `pending` / `running` / `done` / `failed` / `needs-confirmation`
- `naturalSummary`
- `userVisibleResult`
- `createdAt`
- `finishedAt`

### ComponentDraft

对话中生成或修改桌面组件的草案。

字段：

- `id`
- `conversationId`
- `widgetType`
- `title`
- `content`
- `stylePreset`
- `positionHint`
- `sizeHint`
- `reason`
- `status`: `draft` / `confirmed` / `applied` / `cancelled`

### LightToolResult

轻量工具结果，只保存用户能理解的信息。

字段：

- `actionId`
- `summary`
- `displayText`
- `relatedWidgetId`
- `relatedPath`
- `errorMessage`
- `rawHiddenDetails`

### SelfRepairDiagnostic

AI 自检或自修复前先产生的诊断结果。

字段：

- `id`
- `conversationId`
- `scope`: `runtime-data` / `component-config` / `user-wallpaper` / `generated-component` / `core-app`
- `canAutoFix`
- `riskLevel`: `low` / `medium` / `needs-update`
- `userSummary`
- `technicalDetailsHidden`
- `affectedPaths`
- `suggestedAction`

其中 `core-app` 永远不允许直接自动修，只能解释原因、收集日志、建议更新或生成开发侧修复任务。

## 4. 对话体验规则

### 4.1 默认先回应人，再处理事

用户表达情绪时，先接住情绪，再给建议或动作。

```text
用户：今天好烦，事情好多。
灵月：听起来像是被一堆事情同时拽住了。先别急着全解决，我陪你拆成三小块，好吗？
```

### 4.2 工具过程要短、自然、角色化

可以说：

- “我看眼实时天气。”
- “我给你顺手记到桌面上。”
- “我翻一下刚才那条线索。”
- “等我一下，我把它整理成一张小卡片。”

避免说：

- “正在调用 weather 工具。”
- “AgentRun 已进入 verifying。”
- “Permission Engine 返回 needsApproval。”

### 4.3 最终回复只说结果和体感

轻量动作完成后，回复应简短：

```text
放好了，在桌面右上角。标题我用了“今晚别忘”，看起来不会太压画面。
```

不默认展示原始 JSON、完整路径、工具名和长日志。

### 4.4 需要确认时也保持轻

只有这些情况需要确认：

- 会删除、覆盖或移动用户文件。
- 会打开外部应用或网页并可能暴露隐私。
- 会读取明显敏感文件。
- 会生成较大或可能打扰桌面的组件。
- 用户的话本身含糊，动作结果可能不符合期待。

确认文案：

```text
我可以帮你把这 3 个文件挪到“待整理”文件夹。这个动作会改变它们的位置，要现在做吗？
```

按钮：

- `现在做`
- `先预览`
- `算了`

## 5. 桌宠和 UI 反馈

AI 对话的 UI 不只是聊天气泡。桌宠、状态条、过程提示、组件动画都要一起服务角色感。

### 状态映射

| 状态 | 桌宠动作 | UI 反馈 | 说明 |
| --- | --- | --- | --- |
| idle | 待机/眨眼 | 无强提示 | 安静陪伴 |
| thinking | 思考/歪头 | 轻微等待点 | 模型生成中 |
| searching | 翻找/看屏幕 | “我看一下” | 搜索、天气、新闻 |
| writing | 写字/敲字 | “我给你记下” | 便签、清单、组件内容 |
| arranging | 整理/搬动 | 小组件淡入/移动 | 添加或调整组件 |
| happy | 开心/点头 | 完成短句 | 成功完成 |
| concerned | 靠近/担心 | 安慰语气 | 用户压力或负面情绪 |
| confused | 疑惑 | 提一个问题 | 需要用户补充 |

### 过程提示层级

1. 轻动作：只在聊天气泡里说一句。
2. 可见桌面变化：聊天气泡 + 小组件动效。
3. 需要确认：轻确认卡。
4. 失败：说清楚原因，给一个可继续的选择。
5. 高级文件/命令能力：默认折叠到“高级详情”。

## 6. 组件生成流程

### 新建组件

```text
用户：帮我做一个喝水提醒。
灵月：好，我给你做一个小一点的喝水提醒卡，放右下角不挡东西。
```

流程：

1. 识别组件类型和意图。
2. 生成 `ComponentDraft`。
3. 选择默认样式、尺寸和位置。
4. 如果影响较小，直接添加；如果不确定，展示轻确认。
5. 写入组件配置。
6. 桌面组件出现，聊天中给一句自然反馈。

### 修改组件

```text
用户：这个天气卡片太严肃了，换可爱一点。
灵月：懂，给它换成更软一点的样子，颜色也轻一点。
```

流程：

1. 定位当前组件。
2. 生成样式修改草案。
3. 应用样式。
4. 记录修改摘要。
5. 提供“撤回刚才样式”的轻入口。

这里的“撤回”只针对组件配置，不等同于复杂文件 checkpoint。

## 7. 轻量文件与电脑控制

### 推荐能力

- 打开网页、应用、系统设置入口。
- 读取剪贴板并改写成更好的文字。
- 生成一个简单文件到用户选择的位置。
- 把对话内容保存成便签或 Markdown。
- 读取用户明确指定的小文件做总结。
- 简单搜索本地文件名或内容。

### 边界

- 不主动扫描大量私人文件。
- 不默认运行命令。
- 不默认修改已有文件。
- 不默认展示绝对路径。
- 不把每个操作包装成严肃任务流。

### 失败反馈

失败时重点是“我没做到什么、你可以怎么继续”：

```text
我没能打开这个文件，可能是路径已经变了。你可以把它拖进来，我再帮你看。
```

而不是：

```text
Error: ENOENT no such file or directory
```

原始错误可以放进展开详情。

## 8. 当前代码能力重新评估

当前实现已经具备不少偏“Agent”的底层能力，但产品完成度不能按复杂工具数量计算。

### 已经有价值的部分

- 模型 profile 管理和连接测试。
- 流式对话。
- DeepSeek 工具循环兼容。
- Persona 管理。
- 聊天历史写入 SQLite。
- 工具前短句和工具过程交错展示。
- 天气、新闻、搜索、位置、剪贴板、打开链接、系统信息等轻工具。
- 桌宠状态与聊天页主题同步基础。
- 文件/Artifact/审批/checkpoint 骨架可作为高级能力储备。

### 与新方向不匹配的部分

- AgentRun、审批、checkpoint、文件变更审查占比过重。
- 文档和提示词容易把 AI 引向“严肃任务执行者”。
- 工具过程 UI 仍偏日志，不够像角色动作。
- 组件生成/组件控制还没有成为一等能力。
- 伴侣关系、情绪、主动关心和桌宠动作联动仍不足。

### 新口径完成度

| 模块 | 估计完成度 | 判断 |
| --- | --- | --- |
| 基础聊天链路 | 85% | 可稳定对话和流式输出 |
| 模型配置 | 85% | profile、测试、模型列表已具备 |
| 人设基础 | 65% | 有 Persona，但表达层还需要更细 |
| 桌宠/形象联动 | 45% | 有状态基础，动作和情绪联动不足 |
| 记忆系统 | 50% | 有表和总结 worker，召回、人设偏好和私密隔离不足 |
| 轻工具 | 70% | 搜索、天气、新闻、位置等可用 |
| 组件生成/控制 | 20% | 未来核心，当前缺协议和 UI |
| 重型本地 Agent | 60% | 骨架多，但不再作为主线完成度 |
| 整体伴侣体验 | 55%-65% | 底层多，温度和形象反馈还没完全长出来 |

## 9. 后续开发优先级

### P0：让她更像“她”

- 重写系统提示词，减少工具/Agent 术语。
- 明确默认人设、称呼、说话节奏和边界。
- 增加情绪识别与回复模板，但避免机械模板化。
- 聊天等待、搜索、完成、失败都有角色化短句。
- 桌宠动作跟随对话状态。

### P1：对话驱动组件

- 定义组件操作协议：`list_widgets`、`create_widget_draft`、`apply_widget_update`。
- 新增组件草案 UI。
- 支持便签、待办、天气、倒计时、文本卡片的对话生成。
- 支持调整组件样式、位置、大小和内容。
- 组件变更提供轻撤回。

### P2：轻量电脑助手

- 收敛工具列表和提示词，只暴露日常高频能力。
- 打开网页/应用/系统设置。
- 剪贴板润色。
- 简单文件生成和保存。
- 截图与便签。
- 小范围文件读取和总结。

### P3：记忆与关系感

- 伴侣偏好记忆：称呼、语气、颜色、桌面风格。
- 情绪事件记忆：只记重要且可帮助未来陪伴的内容。
- 组件偏好记忆：用户喜欢什么风格和摆放方式。
- 私密记忆隔离。
- 可视化“她记住了什么”的轻量入口。

### P4：高级能力保留但降噪

- 文件写入、checkpoint、审批、Artifact 继续保留在底层。
- 默认 UI 不突出这些概念。
- 只有用户明确进入“高级任务/文件工作”时再展示详细过程。

## 10. 文档使用规则

后续开发 AI 对话相关功能时，优先阅读：

1. [项目状态](../project-status.md) 中的“数据服务与 AI 伴侣”。
2. `memory-system-design.md`。
3. 本文。
4. 只有当用户明确要求复杂文件任务、批量处理、命令执行或编程协作时，才参考旧 AgentRun / checkpoint / approval 代码能力。

判断一个功能是否该做，先问：

- 它会让灵月更像一个有形象的陪伴者吗？
- 它能自然融入桌面组件或桌宠反馈吗？
- 它是不是用户日常会顺口请求的轻量帮助？
- 它会不会把体验变得像工作流软件或开发工具？

如果答案偏向最后一项，就应该降级、隐藏或延后。
